# 設計ドキュメントの作成ルール

このファイルは設計文書・図の形式、描き方と実装との照合の正本とする。共通の実装原則・完了条件は[ルートの規約](../RULES.md)に従う。

このディレクトリは、designアプリに登録して表示する設計ドキュメントのルートです。

- 文章・構成を作成、更新するときは、先に[執筆ガイド](./_guide/writing.md)を読む。
- 図を作成、更新するときは、先に[図のガイド](./_guide/diagrams.md)と、対象のJSON Schemaを読む。

| 作成・変更するファイル | 参照するJSON Schema                                               |
| ---------------------- | ----------------------------------------------------------------- |
| 図のbase.json          | [base.schema.json](./_schemas/base.schema.json)                   |
| 図のview.json          | [view.schema.json](./_schemas/view.schema.json)                   |
| 文書の名前.view.json   | [document-view.schema.json](./_schemas/document-view.schema.json) |

- 設計内容はMDXとbase.jsonに記述し、view.jsonには表示設定だけを置く。
- プロジェクトの実装や資料を確認し、事実・決定事項・未決事項を区別する。
- JSONの項目・型・必須項目・制約はSchemaに従う。データへ未知の項目や$schemaを追加しない。
- Schemaで表せない参照関係やMDXの制限は、各ガイドにも従う。
- 既存の文書、ノード・接続のID、人間が保存した表示設定を尊重する。表示設定は明示的に依頼された場合だけ編集する。
- _guide/と_schemas/は作成支援用の資料として扱い、本文のページや構成図へ混ぜない。

## 業務処理の図示

各役割の責務と依存方向、図の更新が必要になる変更は[backendの規約](../backend/RULES.md)を正本とする。この節では図の単位・描き方・コードとの照合を定める。

| 図の目的                         | ノードと矢印の意味                                             |
| -------------------------------- | -------------------------------------------------------------- |
| 業務フロー図（アクティビティ図） | ノードは処理・判断、矢印は実行順と分岐条件                     |
| 呼び出し構成図                   | ノードはクラスなどの部品、矢印は呼び出す関係。実行順は表さない |

- 一つのActionにつき一つの業務フロー図を基本にし、開始から結果を返すまでの主要な手順を描く。Actionがない単独処理はその業務操作を単位とし、図を作る目的でActionを追加しない。呼び出し構成図は責務やapp間の関係を説明する必要がある場合に補足する。一つの図で実行順と呼び出し関係を混同せず、図の目的と矢印の意味を本文に明記する。
- 処理ノードの`label`には業務上の処理名と担当の役割・クラス・メソッドを併記する。例：`Noteを取り込む（Service: NoteImporter.run）`。`description`には所属app、ソースのリポジトリ相対パス、必要な入力・結果を記す。色や位置だけでAction・Service・Bridge・Modelを区別しない。
- フロー図には条件分岐・繰り返し・正常終了と、業務上重要な失敗経路を示す。分岐の接続には条件を書き、同期呼び出しの次の処理は呼び出しが成功して戻った後に進むことを表す。呼び出し順・戻り値のやり取りを詳しく説明する必要がある場合は、対応する本文で補足する。
- 例外の伝播先、トランザクションの範囲、失敗時に残る変更、再実行時の扱いを図または対応する本文に明記する。DBのロールバックで外部I/Oも取り消せるような図にしない。
- Service内部の詳細なModel操作は、必要に応じてそのServiceの詳細図へ分ける。Model・QuerySet・Managerを描く場合は、実際の検索・検証・保存メソッドを記し、`run()`があるものとして扱わない。
- Bridgeの先は相手appの公開Actionまでを描き、所属appを明示する。相手側の内部処理は相手の設計文書へ分ける。詳細文書へのリンクはノードの`href`を使い、文書への相対パスにする。ソースコードのパスは`description`に記す。
- 図は既存のMDX＋`base.json`の形式で保存する。役割・担当メソッドなどは既存の`label`・`description`で表し、Schemaにない独自属性を追加しない。人が保存した`view.json`と既存のノード・接続IDは、上記の共通規則に従って維持する。
- 図とコードの対応は、対象の`run()`と呼び出し先を読み、入力・結果・処理順・条件・例外・トランザクションの範囲を照合する。図の分類を揃えるために、実装にないService・Bridge・Model操作を補わない。実装済みの動作と未実装の設計案を区別する。
