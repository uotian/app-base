# 執筆ガイド

## 文書の構成

- 文書はMDXで作り、ルートと各階層の入口をindex.mdxにする。
- frontmatterのtitleをページ名、orderを表示順に使う。titleと先頭のH1は揃える。
- 親ページではその階層の構成と直属の責務を説明し、詳細は子ページへ分ける。
- 実装や仕様を具体的に書き、根拠のない評価・宣伝表現・説明の重複を避ける。
- 意味のある見出しを維持し、配置だけのための小見出しを作らない。

## architectureの書き方

- システム全体の構成要素・責務・関係を説明する。
- 最初に構成図と責務表を置き、図の矢印が何を表すか明記する。
- アプリ本体、開発用ツール、配布物、利用者が管理するデータを区別する。
- 生成元と生成先、実行時の依存、外部との境界を説明する。
- ディレクトリ名の列挙だけにせず、各要素の役割を主に書き、対応するパスを添える。
- 各要素の内部構造・操作仕様・実装詳細は担当する文書へ分け、architectureから参照する。
- 構成変更時は、現在の構成に基づいて構成図のbase.jsonと本文を作り直し、不要になった図・説明・リンクを削除する。同じ役割を持つ要素のIDは維持する。
- 人間が保存したview.jsonや文書の「名前.view.json」は自動で作り直さない。

## 使用できるMDX

文章、見出し、リスト、表、コードブロック、リンク、属性なしのdetails・summaryを使える。import・export・JavaScript式・画像・任意のコンポーネントは使わない。

図は独立した行のDiagramで参照する。図・文章・表を並べて読む範囲はLayoutGroup、関連する内容のまとまりはLayoutItemで囲む。

```mdx
---
title: top
order: 0
---

# top

このシステムの目的と対象を説明します。

## 構成

<LayoutGroup id="structure">
  <LayoutItem>

<Diagram src="./_flow" />

  </LayoutItem>
  <LayoutItem>

| 部品      | 責務           |
| --------- | -------------- |
| input     | 入力を受け取る |
| processor | 入力を処理する |

  </LayoutItem>
</LayoutGroup>
```

- LayoutGroupのidは文書内で一意の安定したIDにする。英数字で始め、以降は英数字・ハイフン・アンダースコアを使う。予約名__proto__・constructor・prototypeは使わない。
- LayoutGroupは文書直下に置き、直下の子は属性なしのLayoutItemだけにする。グループを入れ子にしない。
- LayoutGroupは対象の見出しの直後へ置く。見出しの改名だけではIDを変えない。
- 項目はMDXの記述順に表示される。1列でも2列でも意味が通る読み順にする。列数はブラウザで選び、MDXへ列数属性を足さない。

## ファイルとリンク

- 図などの補助データは_flowのように「_」で始まるディレクトリへまとめる。この配下は文書ツリーに表示されない。
- 文書間のリンクは文書ルート内のMDXへの相対パスで書く。絶対パス、アプリの固定URL、文書ルート外の参照は使わない。
- 外部リンクはHTTP・HTTPSを使う。同じページの見出しへのリンクも使える。
- 図のsrcもMDXファイルからの相対パスにする。
- 文書と図を変更したら、参照先・ID・内容の整合を確認する。

## 表示設定

図のview.jsonと文書の「名前.view.json」は任意の表示設定。人間がブラウザで保存した値を、文章の変更に合わせて作り直さない。

明示的に文書配置を編集する場合は、RULES.mdに示すdocument-view.schema.jsonに従い、存在するLayoutGroupのIDだけを使う。図のview.jsonとは保存先を分ける。
