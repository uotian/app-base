# mcp

このファイルはMCPの公開契約・通信境界と結合テストの正本とする。共通の実装原則・完了条件は[ルートの規約](../RULES.md)に従う。

公式Python SDK v2の独立したWeb向けMCPサーバー。Python環境・検査設定・プロセスとimport起点の分離は[共通規約の開発環境の配置](../RULES.md#開発環境の配置)に従う。Electronには同梱しない。

## 配置と責務

| 場所                             | 担当                                                                         | 持ち込まないもの                         |
| -------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------- |
| `src/server.py`                  | 起動引数、サーバー生成、登録一覧のループ実行                                 | 機能固有のimport、ツール本体、HTTP通信   |
| `src/registry.py`                | 全機能のツール登録関数とAPI URL生成関数の一覧                                | ツール本体、通信、自動検出               |
| `src/<機能>/tools/<ツール名>.py` | 入力定義、API呼び出しの手順、Cookie・CSRF、応答検証、出力・MCPエラーへの変換 | 業務処理、DBアクセス、共通送信処理の迂回 |
| `src/<機能>/django/request.py`   | HTTP送信、HTTPエラー・通信失敗を安全なAPI例外へ変換                          | 操作ごとの応答検証、ツール登録           |
| `src/<機能>/<機能>_api_url.py`   | 起動引数のベースURLを検証し、その機能のAPI URLを生成                         | HTTP通信、ツール登録                     |
| `src/<機能>/django/error.py`     | 安全なメッセージを渡すAPI例外の定義                                          | 通信、ツール登録                         |
| `src/<機能>/schemas.py`          | API応答・ツール出力のPydanticモデル                                          | 通信、設定読み込み、ツール登録           |
| `tests/`                         | MCPから実際のHTTP APIへの結合テスト、失敗条件、構成チェック                  | 利用者のDB・設定の変更                   |

- 機能ごとに`src/<機能>/`へまとめる。Noteは`src/notes/`に置く。ツールは`tools/<ツール名>.py`に1ツール1ファイルで置き、入力定義からAPI呼び出し・応答検証・結果の組み立てまで上から追えるようにする。同じ操作の委譲先ファイルを作らない。
- 各ファイルの`register_<ツール名>`関数と対応するAPI URL生成関数を組にして、`registry.py`の`TOOL_REGISTRARS`へ明示的に並べる。`server.py`は一覧をループで呼び、機能固有のモジュールを直接参照しない。
- registryは各機能の登録関数とAPI URL生成関数を参照する。toolsはdjangoのrequest・errorとschemasを参照し、requestはerrorを参照する。逆向きの依存は作らない。errorは他の実装を参照しない。
- `request.py`・`error.py`・schemasは機能内で共有し、操作ごとに複製しない。service層・汎用クライアント基底クラス・自動登録機構を足さない。
- 業務操作はDjangoのHTTP API経由に限定する。backendの実装をimportせず、DB・ORM・ファイルを直接読み書きしない。
- `src/`をimport起点にし、SDKの`mcp`と同名のPythonパッケージを作らない。`__init__.py`や再exportだけのファイルを機械的に追加しない。

## 通信の境界

- HTTP送信は各機能の`django/request.py`だけで行う。toolsから直接`httpx.get()`・`client.post()`・`client.request()`・`client.send()`・`client.stream()`などを呼ばず、共通の`request()`を使う。
- toolsはHTTPクライアントの生成・終了、タイムアウト、Cookie・CSRF、APIを呼ぶ順序、応答検証を担当する。クライアントは`async with`で確実に閉じ、CSRF取得と投稿では同じクライアントのCookieを引き継ぐ。
- `<機能>_api_url.py`はHTTP(S)・ホスト・認証情報・パス・クエリ・フラグメントを検証し、機能のAPIパスを付ける。通信しない。接続先は起動時に確定し、AIが指定するツール引数へ公開しない。
- APIの認証・CSRF保護を省略しない。リダイレクトを自動追跡せず、投稿を自動再試行しない。Cookie・トークン・接続詳細・生のエラー応答をツール出力やログに含めない。
- APIの応答形式はschemas、AI向けの出力への変換はtoolsで扱う。業務ルールの正本はDjango側に置く。

## エラーと公開契約

- 起動設定の不備は`ValueError`で起動を止める。URL解析の`httpx.InvalidURL`も安全なメッセージの`ValueError`へ変換する。
- 想定したHTTPエラー・通信失敗は、requestが安全なメッセージを持つAPI例外（Noteでは`NoteAPIError`）へ変換する。toolsは通信側のAPI例外を`ToolError`へ変換する。tools内の応答検証失敗は安全なメッセージの`ToolError`を直接返し、API例外を経由する二段変換はしない。
- 独自例外の型だけでは情報を隠せない。メッセージは投げる側で整える。プログラム上の不具合まで`except Exception`で一括して利用者向けエラーに変換しない。
- 書き込みツールの説明には公開範囲と副作用を示す。保存結果が不明な失敗では、保存済みの可能性と、再試行前に一覧を確認する必要を伝える。

## ツール追加手順

1. `tools/<ツール名>.py`に登録関数とツールを実装する。名前・説明・引数・annotations・結果・失敗時の動作を定義する。
2. `registry.py`へ登録関数とAPI URL生成関数の組を追加する。同じ機能では既存のURL生成関数を使う。
3. 必要なAPI応答・ツール出力モデルを機能の`schemas.py`に追加する。既存モデルで足りる場合は増やさない。
4. `tests/test_mcp_architecture.py`の許可パス・依存と、MCPクライアントが取得する公開ツールの期待値を更新する。成功・入力不正・API失敗の振る舞いを確認し、書き込みではCSRF・再試行・保存結果不明時の扱いも確認する。
5. `pnpm typecheck:mcp`・`pnpm test:mcp`で個別確認し、ルート規約の完了条件に従い`pnpm check`を実行する。起動入口やコマンドを変えた場合はpackage.json・README・テストの起動方法も揃える。

## 自動チェックと人のレビュー

| 対象                | 自動チェック                                                                                                                                                                                                          | 人が確認すること                                                                                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 配置・依存方向      | 構成テストが許可パスと静的importを検査                                                                                                                                                                                | 責務の妥当性、動的import、間接的な依存                                                                                                                                                              |
| HTTP送信の境界      | ASTで各関数・クラス・モジュールの範囲を分け、HTTPXの直接送信と、その範囲内の単純な代入・with・引数型から分かるClient/AsyncClientの送信を検出。モジュール直下と同じ範囲の別名importに対応。`django/request.py`のみ許可 | 外側の関数から引き継ぐimport・クライアント、関数や属性経由のクライアント、再代入・名前の上書き・別変数への引き継ぎ、getattrなどの動的呼び出し、別のI/O手段による迂回。request内部で行う処理の妥当性 |
| 公開ツール・API契約 | MCPクライアント経由の登録ツール一覧、一覧取得・追加・ページング・入力不正の結合テスト                                                                                                                                 | ツール説明・annotations・公開範囲の妥当性、引数に接続先や秘密情報を露出していないか                                                                                                                 |
| CSRF・失敗時の保護  | CSRF拒否、悪意あるOriginの拒否、API失敗時の生情報非公開、自動再試行なしを既存テストで確認                                                                                                                             | 認証・権限・所有者、エラー文の安全性、保存結果不明時の案内、未テストの失敗条件                                                                                                                      |
| 型・書式            | mypy、Ruff、Prettier                                                                                                                                                                                                  | 型で表せない仕様・業務上の正しさ                                                                                                                                                                    |

ASTチェックは関数間の変数追跡や同じ範囲内の再代入を解析しない。限定した構文の検査であり、HTTP通信が必ず共通処理を通ることを完全に証明しない。検出対象外の書き方も規約の例外ではない。チェックの修正は[規約チェッカーの規約](../scripts/rules/RULES.md)に従う。

## テスト

共通のテスト設計・保護は[testsの規約](../tests/RULES.md)に従う。mypyは`mypy.ini`、pytestは`pytest.ini`を使い、Django用プラグインを読み込まない。

配置変更だけでも既存のMCPクライアント経由のテストを維持する。結合テストは一時SQLite DBでDjangoを別プロセス起動し、準備・確認もHTTP API経由で行う。backendのモデルや設定をimportしない。
